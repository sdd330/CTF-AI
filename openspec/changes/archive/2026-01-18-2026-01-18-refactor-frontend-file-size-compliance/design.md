# 设计文档：前端文件大小合规重构

## Context
前端代码经过之前的 OOP 重构后，虽然已经有了模块化结构（如 `game-state/`、`map/`、`physics/` 等子目录），但主文件（`Game.ts`、`GameStateManager.ts`、`InputManager.ts` 等）仍然过大，超过了200行的限制。这些文件承担了太多职责，需要进一步拆分以符合单一职责原则和代码风格规范。

## Goals
- 将所有前端 TypeScript 文件重构至 ≤ 200 行
- 保持清晰的公共 API，不破坏现有接口
- 使用组合模式而非深度继承
- 提高代码的可读性和可维护性
- 每个模块只负责一个明确的职责

## Non-Goals
- 改变公共 API 或破坏向后兼容性
- 优化性能（本次重构专注于结构，非性能）
- 添加新功能（仅重构现有功能）

## Decisions

### 1. 使用组合模式（Composition Pattern）
**决策**: 所有超过200行的类都将使用组合模式，将职责委托给私有子模块。

**理由**:
- 组合优于继承，避免深度继承链
- 每个子模块可以独立测试和维护
- 保持主类的公共 API 简洁清晰
- 符合单一职责原则

**示例**:
```typescript
// Game.ts (主类)
export class Game extends Phaser.Scene {
  private objectManager: GameObjectManager  // 组合：对象管理
  private flowController: GameFlowController // 组合：流程控制
  private scoreManager: ScoreManager         // 组合：分数管理
  
  // 公共方法委托给子模块
  startOrPauseOrContinue(): void {
    this.flowController.startOrPauseOrContinue()
  }
}
```

### 2. 拆分优先级和顺序
**决策**: 按照依赖关系从底层到高层依次拆分：
1. `debug.ts` (工具类，无依赖)
2. `InputManager.ts` (被多个组件依赖)
3. `GameInitializer.ts` (初始化阶段)
4. `GameStateManager.ts` (状态管理)
5. `Game.ts` (最高层场景)

**理由**:
- 避免循环依赖
- 先拆分底层可以减少后续重构的影响范围
- 按照依赖顺序可以逐步验证每个拆分的正确性

### 3. 子模块命名和位置
**决策**: 
- 为每个管理器创建子目录（如 `input/`、`debug/`、`game/`）
- 子模块使用描述性名称（如 `KeyboardInputHandler`）
- 主文件保留原名称和位置

**理由**:
- 清晰的目录结构便于理解和导航
- 描述性名称明确表达模块职责
- 保留原文件位置确保向后兼容

### 4. 保持公共 API 不变
**决策**: 所有公共方法和属性保持不变，仅内部实现改为委托。

**理由**:
- 不破坏现有代码的使用方式
- 测试代码无需大幅修改
- 用户（其他模块）无感知重构

### 5. 私有子模块不导出
**决策**: 子模块设为私有，不导出给外部使用。

**理由**:
- 封装内部实现细节
- 避免外部直接依赖内部结构
- 保留未来重构的灵活性

## Risks / Trade-offs

### Risk 1: 增加文件数量
- **风险**: 文件从5个增加到约18个，可能增加导航复杂度
- **缓解**: 使用清晰的目录结构和命名约定，每个文件职责单一更易理解

### Risk 2: 测试更新成本
- **风险**: 现有测试可能需要更新导入路径
- **缓解**: 保持公共 API 不变，大部分测试无需修改

### Risk 3: 过度拆分
- **风险**: 可能产生过小的模块，增加理解成本
- **缓解**: 每个模块至少40-50行，确保有足够的内聚性

## Migration Plan

### 阶段1: 拆分工具类（debug.ts）
- 影响范围：最小，仅工具类
- 验证方式：运行单元测试
- 回滚方案：恢复原文件

### 阶段2: 拆分 InputManager
- 影响范围：Player 类和测试
- 验证方式：运行 InputManager 测试和 E2E 测试
- 回滚方案：恢复原文件和导入

### 阶段3: 拆分 GameInitializer
- 影响范围：Game 场景
- 验证方式：启动游戏并测试初始化流程
- 回滚方案：恢复原文件

### 阶段4: 拆分 GameStateManager
- 影响范围：多个管理器和场景
- 验证方式：完整游戏流程测试
- 回滚方案：恢复原文件和相关导入

### 阶段5: 拆分 Game 场景
- 影响范围：主场景逻辑
- 验证方式：完整游戏流程和 E2E 测试
- 回滚方案：恢复原文件
